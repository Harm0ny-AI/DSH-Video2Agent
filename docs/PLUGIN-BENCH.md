# DSH 插件性能与能力基准

本文记录 0.1.0 候选版的一次性能快照：冷启动、CLI/工具延迟、宿主路由、轮询开销，以及这些数字的测量口径。数字来自单台 Windows 开发机上的重复测量，用于说明量级和瓶颈在哪里，不是跨机器基准，也不构成延迟承诺。

## 测量口径

- 在隔离的 DSH profile 和临时 `VIDEO2AGENT_HOME` 上测量，日常使用中的数据不参与；
- 标“冷”的每一行都是新进程（Python 解释器启动计入），标“进程内/暖”的行复用常驻 worker；
- p50/p95 为同一次会话内的重复测量；测量期间机器上还有其它 CPU 负载，重复跑的偏差约 10%；
- 单位：ms（除非另注）。

## 1. 冷启动与内存

| 项 | 值 | 说明 |
| --- | --- | --- |
| `video2agent doctor`（冷） | **525** | 含 Python 启动 |
| 隔离的 `dsh web` 到端口监听 | **≈4.8 s** | 监听后轮询端口测得 |
| DSH 宿主进程 | **301 MB** 工作集 / 3.17 s CPU / 15 线程 | 空闲基线 |
| 浏览器到输入框可见 | **649** | 服务已预热 |
| 客户端 JS 堆 | **38 MB** 已用 / 57 MB 总 | 跑完 UI 流程后 |

CLI 的 ~500 ms 下限来自 Python 解释器启动，不是检索本身；所以短视频上“启动”比“检索”更贵，这是感知速度最大的杠杆。

## 4. 轮询开销

运行中的任务由客户端每 **2.5 s** 轮询一次；每次轮询在宿主侧要起一个 Python 进程读任务状态，实测 p50 **0.5 s**、p95 **1.1 s**，也就是占空比约 20% 单核。任务结束（成功/失败/取消）后立刻停止，空闲时不轮询。

这就是“卡片很轻、但仍有成本”的来源：成本在每次轮询的进程启动，不在渲染（渲染是毫秒级）。降低它只有两条路：拉长间隔（已从 1.2 s 调到 2.5 s），或让宿主缓存/常驻读取；后者是后续优化方向。

## 5. 延迟构成

- **Python 启动**：每次冷调用约 0.5 s；
- **入库**：OCR 主导 —— 6 s 幻灯片夹具 9.33 s 里 OCR 占 8.53 s（6 帧、21 条轨道）；ASR 视模型与时长；
- **检索**：短夹具 1.8–3.0 s，主要是启动 + FTS；长视频的检索与入库数据见 [长视频实测](LONG-VIDEO-BENCH.md)。

## 6. 2026-11 更新（当前版本）

- **读路径拆分**（检索/预览/字幕/map/compare 不再加载媒体与 OCR 栈）：`--version` 478 → **130**；search 503 → **166**；overview 522 → **282**；transcript 503 → **142**；map 493 → **139**；digest 573 → **324**；暖 evidence 487 → **147**。
- **常驻 JSON-lines worker**（每个宿主一个，空闲 10 分钟退出，不预加载 ASR/OCR）：首次 search 158，热 search 16，热 transcript 6，compare 3 段 186，compare 10×5 521，digest 186，暖 evidence 17；worker 失败自动回退到普通 CLI。
- **队列轮询**：每次请求带 `overview=0`，连续 3 次 404 后停止。
- **长视频**：67 分钟入库 61.2 s、72 分钟 75.6 s（AI 字幕）；字幕音频校验每个 16 s 样本约 4.1–4.4 s，永不为此下载模型。

## 8. 已知限制

- 单机、单次会话的测量；不同硬件、不同视频长度的绝对值和这里会有差异；
- 轮询仍是宿主侧的主要运行成本（见 §4）；
- 并发多个 detached 任务时没有干净基准：现有数据是在机器同时跑其它负载时取的。
